# Programming languages

The podcast has interviewed an unusual density of language creators — CLU ([Barbara Liskov](../entities/barbara-liskov.md)), C++ ([Bjarne Stroustrup](../entities/bjarne-stroustrup.md)), Haskell ([Simon Peyton Jones](../entities/simon-peyton-jones.md)), OCaml ([Xavier Leroy](../entities/xavier-leroy.md)), Hack's tech lead ([Dwayne Reeves](../entities/dwayne-reeves.md)), a Julia core contributor ([John Myles White](../entities/john-myles-white.md)), Lua ([Roberto Ierusalimschy](../entities/roberto-ierusalimschy.md)), Lean ([Leonardo de Moura](../entities/leonardo-de-moura.md)), TypeScript and C# ([Anders Hejlsberg](../entities/anders-hejlsberg.md)) — plus practitioners who bet careers on language choices (Rust at Mozilla and Astral, TypeScript at Meta).

## What the guests say

### Languages are born from problems, not from wanting a language

Stroustrup is explicit: "what do I need to build a language" is the wrong question — find a problem no existing language solves. C++ came from his failed attempt to build a distributed Unix when nothing offered both C's hardware access and Simula's classes ([episode](../sources/creator-of-c-bell-labs-negative-overhead.md)). The pattern repeats across episodes: CLU embodied Liskov's data-abstraction answer to the 1970s software crisis ([episode](../sources/turing-award-winner-data-abstraction.md)); Rust was Mozilla's answer to two structural C++ problems, memory-safety exploits and single-threaded engines on multi-core hardware ([Bobby Holley's episode](../sources/mozilla-firefox-cto-on-browser-war.md)); Hack existed to type a giant PHP codebase ([episode](../sources/tech-lead-for-metas-most-used-programming.md)); Julia was designed "to destroy MATLAB" ([episode](../sources/msl-eng-director-promo-hacking-industry.md)). Lua is the purest case of the constraint dictating the language: Ierusalimschy wrote it as an embeddable C library from the first line, with the standalone interpreter as merely a client of that library, and the consequences run all the way down — independent states with no shared global state so a host process can run many at once, and `load()` instead of `eval()` to keep compilation separable from execution ([episode](../sources/creator-of-lua-scripting-programming.md)). Lean is the same pattern with an unusually precise trigger: de Moura had already built Z3, a fully automatic solver that was excellent at finding bugs and "never super successful" at proving their absence, and whose users kept saying "come on, I know the proof. I mean, why can't Z3 find it?" — "that's why Lean started," a language where the human (and now the model) can supply the reasoning step by step ([episode](../sources/creator-of-lean-the-end-of-handwritten.md), [formal-verification](formal-verification.md)).

### Static typing: the podcast's rarest thing — near-consensus

Almost every guest lands on the same side, for different reasons:

- Reeves (Hack): a large codebase is an information-communication problem; types communicate intent, power tooling, and rule out whole error classes — "only solo hobbyists move faster dynamically." Typing one untyped core PHP API surfaced real bugs in ~20% of migrated call sites. His "uncanny valley of type systems": as a codebase approaches full typing, the remaining places where types lie get more off-putting, so things feel worse just before 100% ([episode](../sources/tech-lead-for-metas-most-used-programming.md)).
- Peyton Jones (Haskell): the biggest benefit is maintainability — he refactors 35-year-old GHC "fearlessly" by changing a type and following the wave of errors; weak type systems are strictly worse than strong ones, with dynamic escape hatches for the remainder ([episode](../sources/co-creator-of-haskell-functional.md)).
- Liskov: Python's flaw is modules without encapsulation ([episode](../sources/turing-award-winner-data-abstraction.md)).
- White (Julia): "what makes a language fast is invariants" — dynamic languages are slow because of what they *might* do (R's redefinable braces, Python's rewritable symbol table) ([episode](../sources/msl-eng-director-promo-hacking-industry.md)).
- Stroustrup: static typing was chosen for C++ because embedded systems can't drop into a debugger ([episode](../sources/creator-of-c-bell-labs-negative-overhead.md)); [Boris Cherny](../entities/boris-cherny.md) wrote the TypeScript book and says "thinking in types" changed how he codes more than anything else ([episode](../sources/boris-cherny-creator-of-claude-code.md)); [Charlie Marsh](../entities/charlie-marsh.md) is building the Ty type checker for Python ([episode](../sources/openai-eng-and-dev-tools-founder.md)).

- Hejlsberg (TypeScript, 2026-08-17) is the industrial-scale instance of the consensus, and his version is the strangest: TypeScript's types are *purely* a tooling artifact — "the types have no impact whatsoever on the runtime behavior of the code," since the compiler transpiles to JavaScript rather than generating machine code. The whole apparatus exists for statement completion, refactoring and guidance. He credits Brendan Eich's three-to-four-week design for the parts worth keeping (first-class functions and closures) and holds that a type checker is what makes the rest survivable: "TypeScript has managed to capture all the badness and park it." The result passed JavaScript and Python to become the most-used language on GitHub last year — a layer on top of another language outranking every language it sits above ([episode](../sources/creator-of-typescript-10x-faster.md)).
- Leroy (OCaml): JavaScript is "the ultimate dynamic language" and its runtime-redefinable method invocation and call-stack introspection are "a security nightmare... completely unnecessary"; OCaml's type inference gets conciseness without giving up static checking — constraint solving where leftover unconstrained types become polymorphism for free (Milner's insight), at the price of confusing error messages and poor interaction with subtyping ([episode](../sources/creator-of-ocaml-functional-programming.md)).

De Moura sits at the far end of the same axis, where types stop being a checking aid and become the proof language itself ([episode](../sources/creator-of-lean-the-end-of-handwritten.md)). In Lean, proof checking *is* type checking, and dependent types let a value appear in a type: a structure field whose type is a proof that x > y, or a function that cannot be called without evidence that y ≠ 0. "You don't have to invent invariants" — the invariant is the signature. His choice of dependent type theory over the far-easier-to-implement higher-order logic was made on user grounds rather than aesthetic ones: Jeremy Avigad convinced him he would never attract Fields-Medal-level mathematicians otherwise, because abstract math needs structures as first-class citizens (a function taking a group and returning a group) and higher-order logic forces "encoding tricks. It's a mess." He reports unanimity among the serious users (Tao, Kontorovich, Avigad, Buzzard, Massot) and draws the general lesson: "it's totally okay to say I don't care about this community. But if you care, listening to what they really want is important." The standing objection to dependent types — supplying all those proofs is tedious — is exactly what AI removes.

The one deliberate dissent is pedagogical, not technical: [David Malan](../entities/david-malan.md) still starts CS50 with C — not for types but because it's closest to hardware, forcing students to build hash tables and linked lists before week 6 collapses it all into one line of Python ([episode](../sources/harvard-professor-cs50-what-matters.md)).

### Memory safety: the sharpest disagreement in the series

Peyton Jones says C's unchecked mutation means the Internet's infrastructure is "a boat built out of paperclips" — writing it in Haskell/ML would remove ~99% of exploits by construction ([episode](../sources/co-creator-of-haskell-functional.md)). Stroustrup's response to the memory-safety campaign: "I'm so tired of that" — over 90% of exploited C++ safety bugs come from C-style code with raw pointers, hardened libraries already exist, C++26 standardizes a hardened option, and his profiles work aims at enforceable-by-default guarantees against committee members "devoted to their old code" ([episode](../sources/creator-of-c-bell-labs-negative-overhead.md)). The practitioners have voted with their feet: Holley co-evolved Rust with Servo and shipped its parallel CSS engine as Firefox Quantum ([episode](../sources/mozilla-firefox-cto-on-browser-war.md)), and Marsh — who chose Rust "largely because of hype" and now calls it the best possible choice — "absolutely would not start a new project in C/C++ today" ([episode](../sources/openai-eng-and-dev-tools-founder.md)). Peyton Jones frames Rust as moving C's "useful but unsafe" quadrant toward safety, while Haskell climbed toward usefulness from the opposite corner ([episode](../sources/co-creator-of-haskell-functional.md)).

Leroy (2026-07-20) adds a caveat that tempers the practitioners' Rust enthusiasm without contradicting the safety case: Rust is "the finest language I know for manual memory management," but manual is not automatically faster — GC costs 10–30% at runtime, yet manual-memory code that defensively copies (or unshares to satisfy ownership) can lose to a garbage collector, and OxCaml-style stack allocation wins less than expected because short-lived objects are already nearly free for a generational GC. The GC-vs-manual divide, not safety, is for him the real line between OCaml and Rust ([episode](../sources/creator-of-ocaml-functional-programming.md)).

### Who should be allowed to design a language

This is the corpus's cleanest head-to-head disagreement, and it is about governance rather than syntax. Roberto Ierusalimschy (2026-08-03) argues that conceptual integrity — the parts cohering — is structurally unavailable to committees, because the incentives are asymmetric: people fight far harder to get their own feature in than anyone fights to keep features out, so a committee language ratchets toward accumulation. Small teams work because "everybody knows what everybody else is thinking," and his default is refusal — "when in doubt, the rule is always don't put it... we can always add that later" ([episode](../sources/creator-of-lua-scripting-programming.md)).

Anders Hejlsberg (2026-08-17) is the case neither position predicts. TypeScript is a small-team design in Ierusalimschy's sense — Hejlsberg is still writing the compiler himself — but its constraint came from neither a committee nor a benevolent dictator: the language it extends is standardized by TC39 and moves independently, so TypeScript's design freedom is bounded by a body it does not sit on. His account of what that discipline bought is the "capture all the badness and park it" strategy: rather than fight JavaScript's quirks (automatic conversions, `==` vs `===`) he fenced them behind a checker ([episode](../sources/creator-of-typescript-10x-faster.md)). It is conceptual integrity purchased by *accepting* someone else's design rather than by controlling one's own.

Bjarne Stroustrup's account of C++ is the direct rebuttal, from experience: standardization was *forced* on him in 1989 by IBM and HP representatives whose organizations could not depend on a corporate-owned language, and without it he believes C++ would have "faded into an academic cube language" ([episode](../sources/creator-of-c-bell-labs-negative-overhead.md)) — while elsewhere in the same episode complaining about committee members "devoted to their old code," which is Ierusalimschy's point made from the inside. Xavier Leroy sits nearer Ierusalimschy in practice: OCaml's design stayed with a small Inria group, and the multicore memory model was hard precisely because Java needed five committee iterations and C++11's is "extremely complex" ([episode](../sources/creator-of-ocaml-functional-programming.md)). The unresolved tension: small teams produce coherence, committees produce the institutional durability that lets an industry build on you.

Ierusalimschy's two most-argued-with decisions show the philosophy applied. Lua shipped with no boolean type at all (following C's 0/non-zero convention); `false` was added only because tables needed to distinguish an absent key from a key whose value is false, and `true` then followed for symmetry — "true is almost useless." And on 1-based indexing: "only in programming language there is this idea of zero." His history is that Fortran and Pascal allowed arbitrary index bases, 0-indexing won because C won and languages copied C's syntax, and in C indexing is "just an illusion" over pointer arithmetic — 0 is an implementation requirement, not a conceptual one. For end-user programmers, he argues, "the first element is 0" is simply the harder thing to explain ([episode](../sources/creator-of-lua-scripting-programming.md)).

### Runtimes, embedding, and what "compiled" means

Ierusalimschy gives the corpus's most concrete account of the machinery under all of this ([episode](../sources/creator-of-lua-scripting-programming.md)). "Compiled" and "interpreted" describe a toolchain, not a language — you could compile Python or interpret C (badly); what forces a compiler into the runtime is `eval`-style dynamic code generation. The real performance lever is type information: with types known at compile time you emit the integer add directly, and without them every operation pays for a check and possible coercion — an implementer's restatement of John Myles White's "what makes a language fast is invariants" ([episode](../sources/msl-eng-director-promo-hacking-industry.md)).

On JIT, LuaJIT (Mike Pall) is a *trace* compiler: it records a hot path, through inlined calls, until the loop closes, then emits code specialized to the observed types. The hard parts are machine dependence and deoptimization — reconstructing interpreter state from compiled registers when a trace's assumptions break, where "you don't even have a call stack because you didn't do the calls." Pall's answer was a pseudo-assembler retargeted across architectures; standard Lua takes the opposite trade and buys portability by compiling to bytecode and interpreting in C. He also credits Lua's benchmark edge over Python to something unglamorous: "most of the virtual machine fits in your cache."

Cross-language calls are function pointers in both directions — the host registers named C function pointers into a Lua state and the interpreter invokes them on a call instruction, while a Lua function is a bytecode array C can hand back to the interpreter, so calls nest arbitrarily. The consequence he emphasizes is security: a Lua state can only reach what the host registered, making the host's registration list the entire attack surface. His example is a financial firm that embedded Lua inside Python so users could script against a whitelist without touching program state ([systems-design](systems-design.md)).

### Adoption is a strategy problem

Contrasting playbooks, explicitly at odds:

- Stroustrup rode compatibility and standardization: C++ reused C as its portable assembler ("we can have Dennis Ritchie's mistakes, which we know, and my mistakes, which we don't know yet — so we'll take Dennis's"), was pushed into ISO standardization by IBM/HP who couldn't depend on a corporate-owned language, and grew 10–12x on a $5,000 marketing budget while Sun spent millions on Java ([episode](../sources/creator-of-c-bell-labs-negative-overhead.md)).
- Peyton Jones ran the opposite experiment: Haskell's "avoid success at all costs" deliberately refused to compromise its core principle to chase users ([episode](../sources/co-creator-of-haskell-functional.md)).
- Liskov deliberately kept CLU a research artifact rather than productizing it — its ideas won through Ada and Java instead ([episode](../sources/turing-award-winner-data-abstraction.md)).
- Marsh argues developer marketing is underrated — you have ~10 seconds to convey why a project matters; Ruff's viral benchmark graph was "priceless" ([episode](../sources/openai-eng-and-dev-tools-founder.md)). Reeves adds the inside-a-company version: the migration became real when the "uncanny valley" metaphor became the Hack team's rallying vision ([episode](../sources/tech-lead-for-metas-most-used-programming.md)).
- Hejlsberg's TypeScript ran the "fix it, don't replace it" play and he names the comparison directly: CoffeeScript and Dart both declined, while TypeScript set out to repair JavaScript rather than supersede it ([episode](../sources/creator-of-typescript-10x-faster.md)). Two structural advantages carried it. First, self-hosting: writing the compiler in JavaScript made the team daily users of their own product and let it run everywhere JavaScript ran, including in a browser, which native code could not do before WebAssembly — "if you can self-host in the ecosystem that you want to be a part of, that is dramatically better than targeting from outside." Second, the host language's own ubiquity: he contrasts JavaScript's genuine run-anywhere reach with Java, which never achieved universal deployment.
- Leroy's OCaml found adoption by accident of fit: designed for theorem provers and DSLs, it won systems users (Cornell's Ensemble, MirageOS) because a low-latency GC plus predictable cost model suited network code — and one Ensemble PhD student, Yaron Minsky, took it to Jane Street, which now uses OCaml itself as a hiring filter ([hiring-and-interviews](hiring-and-interviews.md)) ([episode](../sources/creator-of-ocaml-functional-programming.md)).

### Where innovation comes from has inverted

Leroy: the truly innovative early languages (ALGOL, Lisp, Prolog, Smalltalk) came from academia while industry built "uglier" practical ones (Fortran, COBOL, PL/I); now industry transfers research fast and ships what academia can't — Java mainstreamed GC and type safety within two years after decades of "crazy academics in the ivory tower," Swift popularized ADTs and pattern matching, and Rust industrialized 2000s academic safe-low-level-programming results that "were basically never implemented in any language." When he was hired at Inria he was told "there's no future in PL research — industry has decided it will be C forever"; Java disproved it, and he finds industry's continued appetite for new languages "extremely encouraging" ([episode](../sources/creator-of-ocaml-functional-programming.md)). This squares with Liskov keeping CLU a research artifact whose ideas won through Ada and Java ([episode](../sources/turing-award-winner-data-abstraction.md)) and with Peyton Jones needing Epic's muscle to push Verse ([episode](../sources/co-creator-of-haskell-functional.md)).

### Performance philosophy

Stroustrup's "negative overhead abstraction": more type information feeds the optimizer, so C++ can beat C, and 1990s-clever hand optimizations are often pessimizations on modern hardware — his first optimization step is deleting the clever code ([episode](../sources/creator-of-c-bell-labs-negative-overhead.md)). White: "any code that's slow is slow because it's doing stuff it doesn't need to do" ([episode](../sources/msl-eng-director-promo-hacking-industry.md)). Marsh cautions the language is only the floor: uv's speed comes as much from architecture (cache design, packing >90% of version objects into a single u64) as from Rust ([episode](../sources/openai-eng-and-dev-tools-founder.md)).

Hejlsberg's account of the TypeScript-to-Go port is the corpus's most detailed worked example of when a language change is actually the right lever, and most of it is an argument for waiting ([episode](../sources/creator-of-typescript-10x-faster.md)). JavaScript's 2–3x penalty against native was survivable for a decade — V8's optimization work is what made writing a compiler in JavaScript defensible in the first place, and "often performance of your code isn't the bottleneck." What was not survivable was concurrency: JavaScript is single-threaded and web workers cannot share data structures, so as "Moore's Law has stopped giving us faster CPUs, it's giving us more CPUs," the compiler could not follow the hardware. Two other pressures accumulated underneath: codebase scale that nobody forecast in 2012 (VS Code is ~2.3 million lines) and the compiler's own slow drift — TypeScript 6 runs at roughly 50% the speed of TypeScript 1.5, because projects grew and type checking got more sophisticated.

The language choice then fell out of a decision made earlier: they ported rather than rewrote, to preserve semantics and backward compatibility, which meant keeping a codebase that assumes garbage collection and first-class functions. That eliminated Rust on two counts — no GC, and a borrow checker that cannot express the circular structures a compiler is made of (parent pointers, recursive types, symbol references). "We tried, and it just wasn't feasible." This is a useful qualifier on the corpus's otherwise strong Rust default (Marsh, Holley): the argument for Rust in [Marsh's episode](../sources/openai-eng-and-dev-tools-founder.md) is about *new* systems software, and Hejlsberg's counter-case is specifically about porting a large GC-assuming codebase — which is also where [Leroy](../entities/xavier-leroy.md)'s GC-versus-manual caveat lands.

### Languages in the LLM era

Peyton Jones thinks LLMs "may be the best thing that's happened to statically typed languages" — the compiler prunes the model's generation space in a tight loop ([episode](../sources/co-creator-of-haskell-functional.md)). Leroy independently confirms the mechanism from the OCaml side (2026-07-20): type systems demonstrably help LLM generation, models write OCaml about as well as popular languages despite far less training data, and his hope is that the safer languages win the LLM decade — with C/C++-to-Rust translations (one he saw was entirely `unsafe` blocks) and functional-code-to-proof-assistant migrations as the likely big rewrites ([episode](../sources/creator-of-ocaml-functional-programming.md), [formal-verification](formal-verification.md)). Stroustrup is the skeptic for safety-critical code: LLM output brings bugs, bloat, and an unsolvable validation burden, and he channels Dijkstra — natural language is too ambiguous to be a programming language ([episode](../sources/creator-of-c-bell-labs-negative-overhead.md)); Leroy's economic version of the same point is that "every new line of code is a liability" — generation cost falls to zero while checking cost doesn't ([episode](../sources/creator-of-ocaml-functional-programming.md)). Ierusalimschy (2026-08-03) adds the inversion neither camp had stated: if the human's remaining job is reading and verifying rather than writing, then simplicity becomes *more* valuable under AI, not less — the language must let you "really understand that the code that you are seeing does what you think it should do." His cost analysis is the reason: "implementation is the part that AI can really help you. It's not a really important cost," so what remains expensive is the learning burden and cognitive load that language design actually controls, and AI does not do the maintainability reasoning a designer does. He is otherwise unwilling to forecast at all — "it's completely feasible that we won't have programming languages" ([episode](../sources/creator-of-lua-scripting-programming.md)). Note that this cuts against Peyton Jones's and Leroy's shared bet on *static types* as the LLM-era advantage: Lua is dynamically typed, and Ierusalimschy locates the advantage in readability instead. De Moura (2026-08-10) is the fourth position and the most radical: if the language can carry a machine-checked proof, the property that matters is neither readability nor type-driven pruning but *provability*, and the question of how the code reads disappears — "it doesn't really matter how the code has been written. What matters? The specification level" ([episode](../sources/creator-of-lean-the-end-of-handwritten.md)). He expects Lean and Rocq to go mainstream on that basis, noting the frontier labs only recently began training seriously on formal verification with real RL pipelines, so the cost curve has barely started. Two second-order effects he draws out: the long-standing ergonomic objection to functional programming stops mattering when a human isn't the author ([functional-programming](functional-programming.md)), and language *extensibility* becomes an AI feature — because Lean is implemented in Lean, models write Lean metaprograms unprompted to test their own hypotheses about why something fails. Anders Hejlsberg (2026-08-17) adds the fifth position, and it is the only one about the *ecology* of languages rather than about what a language does for a model. AI entrenches incumbents: models are best at whatever they saw most in training, and teaching one a niche language burns prompt tokens, so the already-rising bar for a new language — compiler, tooling, language services, debugger, profiler, frameworks, code generators across multiple targets — rises again ([episode](../sources/creator-of-typescript-10x-faster.md)). He also closes off the argument that languages themselves become vestigial: a program in source text is the most compressed representation available and the closest to the meaning, while machine code carries substantial noise (memory addresses, register allocation) irrelevant to the logic — "teasing the truth out of that noise is harder than having a program where the variable is called I," so models, like humans, work better at higher abstraction. Note what this does to Ierusalimschy's forecast that we may not have programming languages at all: Hejlsberg agrees with his premise that AI favors incumbents and disagrees with the conclusion, on information-theoretic rather than sociological grounds.

Malan splits the difference in the classroom: no Copilot on problem sets (it would autocomplete the whole assignment from a filename), unlimited use of a deliberately less-helpful tutor ([episode](../sources/harvard-professor-cs50-what-matters.md)).

## Practical takeaways

- Pick languages the way creators design them: start from the problem, not the language ([Stroustrup](../sources/creator-of-c-bell-labs-negative-overhead.md)).
- At industry scale, choose static types; treat a large codebase as a communication problem ([Reeves](../sources/tech-lead-for-metas-most-used-programming.md), [Peyton Jones](../sources/co-creator-of-haskell-functional.md)).
- Expect a typed-migration to feel worst just before completion — plan for the uncanny valley ([Reeves](../sources/tech-lead-for-metas-most-used-programming.md)).
- For new systems code, the practitioners' default is Rust; the C++ camp's counterargument is hardened profiles plus existing code bases ([Marsh](../sources/openai-eng-and-dev-tools-founder.md), [Stroustrup](../sources/creator-of-c-bell-labs-negative-overhead.md)).
- Learn a language from another paradigm to escape monoglot thinking — even Stroustrup recommends ML/Haskell ([Stroustrup](../sources/creator-of-c-bell-labs-negative-overhead.md)).
- Speed comes from invariants and architecture; delete clever code before adding it ([White](../sources/msl-eng-director-promo-hacking-industry.md), [Marsh](../sources/openai-eng-and-dev-tools-founder.md)).
- Learn one level below the abstraction you work at — the CS50 argument for C ([Malan](../sources/harvard-professor-cs50-what-matters.md)); Ierusalimschy's version is to learn a *historical* assembly (Intel 8080), because modern ISAs are too complex to learn from ([episode](../sources/creator-of-lua-scripting-programming.md)).
- Default to leaving the feature out; you can add it later, and you usually can't remove it ([Ierusalimschy](../sources/creator-of-lua-scripting-programming.md)).
- Read old languages (Scheme, SNOBOL) for design diversity — modern ones "tend to be too uniform" ([Ierusalimschy](../sources/creator-of-lua-scripting-programming.md)).
- Design for a named community and then actually serve it; de Moura took the much harder implementation (dependent types over higher-order logic) and same-day feature turnaround because mathematicians were the users he wanted ([de Moura](../sources/creator-of-lean-the-end-of-handwritten.md)).
- Make the language extensible in itself if you want an ecosystem you don't have to staff — Lean's outside contributors built an English-prose proof layer and a protocol-verification DSL without ever contacting the core team ([de Moura](../sources/creator-of-lean-the-end-of-handwritten.md)).
- If you want to serve an ecosystem, self-host inside it rather than target it from outside — you become your own daily user and you inherit its reach ([Hejlsberg](../sources/creator-of-typescript-10x-faster.md)).
- Improving an incumbent language beats replacing it; CoffeeScript and Dart went one way, TypeScript the other ([Hejlsberg](../sources/creator-of-typescript-10x-faster.md)).
- Change languages for a property you cannot get otherwise (shared-memory concurrency), not for a constant factor; and port rather than rewrite if backward compatibility is the product ([Hejlsberg](../sources/creator-of-typescript-10x-faster.md)).
- Budget for the bootstrap: self-hosting Lean 4 meant ~100,000 hand-written lines, deliberately bare-bones features, and proofs constructed with no interactivity — "almost like programming in assembly" ([de Moura](../sources/creator-of-lean-the-end-of-handwritten.md)).
