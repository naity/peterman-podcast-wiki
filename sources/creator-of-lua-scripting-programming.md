# Creator of Lua: Scripting, Programming Languages, Predictions | Roberto Ierusalimschy

Roberto Ierusalimschy designed Lua, the small embedded scripting language that ended up inside World of Warcraft, Roblox, Redis, nginx and an enormous amount of unglamorous industrial software. Ryan Peterman starts from a question he had at Instagram — how does a Python codebase actually call into C++? — and gets a working explanation of cross-language calls, JIT compilation, and what "compiled vs interpreted" really means, before turning to design philosophy: why committees produce bad languages, why Lua had no booleans, why it indexes from 1, and why he thinks AI makes simple languages *more* valuable rather than less ([programming-languages](../concepts/programming-languages.md)).

## Key takeaways

- **Lua is a library that happens to ship a binary, and everything follows from that.** It was written as an embeddable C library from the start; the `lua` command-line program is just a client of it. That forces design choices most scripting languages never face: no shared global state (independent Lua states so a host process can run several at once), and `load()` instead of `eval()` to keep compilation and execution separate. He distinguishes *embedding* (the host owns the process and calls into the language) from *extending* (the language calls out to native code) — most scripting languages do one well; Lua targets both ([developer-tools](../concepts/developer-tools.md)).
- **Lua vs Python is a philosophy split, not a quality ranking.** Python optimizes for developer convenience with a large standard library; Lua stays minimal and expects the host application to supply domain functions. He is explicit about the ceiling: Lua "doesn't want to compete with C or C++." His explanation for beating Python on benchmarks is architectural rather than clever — "most of the virtual machine fits in your cache."
- **How cross-language calls actually work.** Function pointers in both directions: the C host registers named C function pointers into a Lua state, and when the interpreter hits a call instruction it looks up and invokes the pointer; in reverse, a Lua function is just a bytecode array that C hands back to the interpreter. Calls nest arbitrarily (Lua → C → Lua → C). The consequence he emphasizes is security: a Lua state can only reach functions the host explicitly registered, so the host defines the entire attack surface. His example is a financial firm that embedded Lua *inside Python* so users could write scripts against a whitelist of authorized functions without touching program state ([systems-design](../concepts/systems-design.md)).
- **JIT, explained through LuaJIT.** Mike Pall's LuaJIT is a *trace* compiler: it records a hot execution path — through inlined calls — until the loop closes, then emits code specialized to the observed types. The hard parts are machine dependence and deoptimization: when a trace's type assumptions break you must reconstruct interpreter state from compiled registers, and "you don't even have a call stack because you didn't do the calls." Pall's answer was a pseudo-assembler retargeted across architectures. Standard Lua instead compiles to bytecode and runs a C interpreter loop, buying portability from the C compiler.
- **"Compiled" and "interpreted" describe toolchains, not languages.** You could compile Python or interpret C (badly). What forces a compiler into the runtime is `eval`-style dynamic code generation. And the real performance lever is type information: if types are known at compile time you emit the integer add directly; otherwise every operation pays for a check and possible coercion.
- **Conceptual integrity, and why committees can't have it.** "A camel is a horse designed by a committee" — his argument is about an asymmetry in incentives: people fight far harder to get their feature in than anyone fights to keep features out, so committee languages ratchet toward accumulation. Small teams work because everyone knows what everyone else is thinking, and the default answer is no: "when in doubt, the rule is always don't put it... we can always add that later" ([language design](../concepts/programming-languages.md)).
- **The two design decisions people argue with him about.** Lua originally had no booleans (C's 0/non-zero convention); `false` was added only because tables needed to distinguish an absent key (nil) from a key whose value is false, and `true` came along for symmetry — he concedes "true is almost useless." On 1-based indexing: books have a chapter 1, "only in programming language there is this idea of zero." His history is that Fortran and Pascal allowed arbitrary bases, 0-indexing won because C won and everyone copied C's syntax, and in C indexing is "just an illusion" over pointer arithmetic — 0 is required by that implementation, not by the concept. For Lua's target audience of end-user programmers, "the first element is 0" is the harder thing to explain.
- **On AI, an argument that cuts against the obvious one.** He refuses to predict — "if you go to an extreme, it's completely feasible that we won't have programming languages" — but the conclusion he commits to is that AI makes simplicity *more* important, because the human's remaining job is reading: "it's even more important for the language to be simple, to be understandable, for you to be able to really understand that the code that you are seeing does what you think it should do." He also splits the cost structure: "implementation is the part that AI can really help you. It's not a really important cost" — what stays expensive is the learning burden and the cognitive load on the reader, which is exactly what language design controls ([ai-era-engineering](../concepts/ai-era-engineering.md)).
- **Career advice from someone who declines to forecast.** Asked whether young people should study CS: "nobody has any idea what the world, your profession, will be like in four years from now." His conclusion is not reassurance but a change of criterion — choose by genuine interest rather than employability, because the employability forecast is worthless. "I program because I like that" ([regrets-and-advice](../concepts/regrets-and-advice.md)).
- **Three languages to become a better engineer.** Haskell, for what rigorous typing does to the shape of the work — "in C you really spend one week to make it efficient, and then you spend one year to make it correct. In Haskell, you spend one week to make it correct" ([functional-programming](../concepts/functional-programming.md)). A *historical* assembly language such as the Intel 8080, because modern assembly is too complex to learn from ([computer-architecture](../concepts/computer-architecture.md)). And Scheme, for its "economy of ideas." He adds SNOBOL as a pattern-matching pioneer, and argues for reading old languages generally because "nowadays a lot of languages tend to be too uniform."
- **Advice to his younger self: there is no shortcut for time.** "To know a lot of stuff, you really have to study a lot of stuff. And it takes time." He is pointed about the "Learn Lua in 30 minutes" genre — you can learn the syntax that fast and still not understand the language for years.
