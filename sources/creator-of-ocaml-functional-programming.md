# Creator of OCaml: Functional Programming, Formal Verification, Programming Languages | Xavier Leroy

Xavier Leroy created OCaml at Inria and later led CompCert, the formally verified C compiler proved correct in the Coq/Rocq proof assistant. The conversation is a language-designer's office hours: what makes OCaml a functional language you can do systems programming in, honest comparisons with Rust and JavaScript, how type inference actually solves constraints, a concrete walkthrough of formal verification and proof assistants like Lean, why multicore OCaml took until 2022, how foreign function interfaces work, and a sharply skeptical take on the economics of LLM-generated code — plus where he thinks proof assistants could rescue it.

## Key takeaways

- OCaml's niche: a fine functional language that is also "a fairly decent systems programming language" — predictable cost model, low-latency GC, full imperative power ([functional-programming](../concepts/functional-programming.md), [programming-languages](../concepts/programming-languages.md)). Cornell's Ensemble network stack proved it in the late '90s (running GC while packets were in flight cost nothing); Ensemble PhD student Yaron Minsky then took OCaml to Jane Street, still its biggest industrial user.
- The main dividing line vs Rust is memory management, and manual is not automatically faster: Rust is "the finest language I know for manual memory management," but GC overhead (10–30% runtime) can beat C-style code that defensively copies because ownership is unclear, and GC allows free sharing where Rust's ownership discipline forces unsharing and more memory. Jane Street's OxCaml experiments (Rust-inspired stack allocation) win less than people expect, because stack allocation only helps short-lived objects that are already cheap for a generational GC.
- JavaScript is "the ultimate dynamic language" and he's not a fan: runtime-redefinable method invocation and call-stack introspection are "a security nightmare... completely unnecessary" — though its Lisp-heritage functional core (via Brendan Eich) is decent.
- On Rob Pike's "Googlers can't understand a brilliant language" quote: functional programming is not fundamentally harder, the quote describes Google's hire-fresh-and-train-internally model; Jane Street uses OCaml as a deliberate [hiring filter](../concepts/hiring-and-interviews.md) — fewer applicants, more interesting backgrounds. And "Python is 50% functional language," so most programmers are halfway there.
- Type inference = constraint solving ("a little bit like Sudoku"): collect equations from uses, solve; no solution = type error, multiple solutions = pick criteria. Robin Milner's beautiful discovery: unconstrained leftover types ARE polymorphism — parametric polymorphism falls out of inference for free. Trade-offs: confusing error messages (the reported site isn't the source), and subtyping/OO-style genericity combines badly with inference, forcing a design choice.
- [Formal verification](../concepts/formal-verification.md) explained from Dijkstra's "testing can only show the presence of bugs" up through proof assistants (Lean, Coq/Rocq, Isabelle): specifications range from "never crashes / all array accesses in bounds" to precise floating-point error bounds; provers record machine-recheckable proofs. His CompCert C compiler is proved to emit assembly faithful to the source — a proof that would be "several thousand pages" on paper, and mechanization is what lets you evolve the program without regressions. The other landmark: seL4, 8,000 lines of microkernel C, every line proved. The halting problem forbids a universal termination analyzer, not termination proofs for the programs you actually care about.
- Why multicore OCaml took until 2022: not just reimplementing the allocator/GC for concurrency (done largely by OCaml Labs, Cambridge), but the memory-model design problem — Java needed five iterations ("impossible predictions where the past depends on the future"), C++11 is still extremely complex, and type-safe languages must guarantee well-typedness under data races. He also never liked shared-memory concurrency: it's "like communicating with your neighbor by breaking into their house and moving the furniture around" — he preferred Erlang-style message passing but never landed a design that answered the copying-cost objection.
- FFIs are "a dirty part of programming language implementation": control transfer is easy; the hard part is mediating different data representations (boxed floats, arrays-of-pointers vs flat arrays) and making C code cooperate with the GC. He is "a firm believer in static linking."
- On the [AI era](../concepts/ai-era-engineering.md): "the cost of writing code maybe [drops to zero], but what about checking it?... every new line of code is a liability." The idea that humans will review all AI output "is just wrong — there's too much of it, and it's not pleasant either." CompCert/OCaml already get AI-generated bug reports (~1 good in 10, each pages long with repro cases that reproduce nothing), and he may ban AI-generated contributions ([open-source](../concepts/open-source.md), [ai-coding-tools](../concepts/ai-coding-tools.md)). The technical way out: make AI emit machine-checkable Lean/Coq proofs alongside its code — but then the hard problem moves to where specifications come from, and an unsatisfiable precondition vacuously "verifies" anything.
- LLMs handle OCaml about as well as popular languages despite less training data, and type systems demonstrably help generation; his hope for the 10-year landscape is that the safer languages win. Likely LLM-era migrations: C/C++ to Rust (he's seen one "translation" that was entirely unsafe blocks), and functional code into proof-assistant languages as a first step toward proofs.
- PL innovation has inverted: ALGOL/Lisp/Prolog/Smalltalk came from academia while industry made "uglier" languages (Fortran, COBOL); now industry transfers research fast — Java mainstreamed GC and type safety in two years after decades of "crazy academics in the ivory tower," Swift popularized ADTs, and Rust industrialized 2000s academic safe-low-level-programming results that academia itself could never have shipped. When he was hired at Inria he was told "industry has decided it will be C forever"; Java proved industry still bets on new languages.
- Books: *Programming Pearls* (Bentley) — timeless portrait of how talented programmers think, including "knowing when to stop"; *How to Design Programs* (Felleisen et al.) — opinionated, "almost mystical," but a great attempt at teaching design-before-code. Advice to younger self ([regrets-and-advice](../concepts/regrets-and-advice.md)): he specialized in PL research too early — get a broad CS foundation (computability, complexity) even when it looks irrelevant; quantum computing is making him relearn the theory he skipped.

## Notable quotes

- "Testing can only show the presence of bugs, but not their complete absence." — Xavier quoting Dijkstra, ~22:25, introducing formal verification
- "It's a bit like if you want to communicate with your neighbor, then you break into their house and move the furniture around, and then when they are back they say, 'Oh, something was moved. So it's probably Ryan who's trying to tell us something.'" — Xavier on shared-memory concurrency, ~42:19
- "Well, the cost of writing code maybe, but what about checking it, making sure it is correct?... For me, every new line of code is a liability... I want 50 lines of code that have been thought through." — Xavier, ~59:35
- "Maybe this will be the decade of formal verification of software. We've been waiting for that for 50 years. Maybe it will finally take off." — Xavier, ~01:18:09
